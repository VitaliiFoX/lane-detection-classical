# Підготовка до захисту — Сивопляс Максим

Моя зона: пайплайни **p3 «Вид зверху»** і **p4 «Top-hat»**, їхні методи
(перспектива, Прюітт, ковзні вікна, морфологія, Кенні), спільні модулі `roi`,
`synthetic`, `checks`, `report`, а також перетворення Хафа (спільне, ADR-0006)
і Собель як частина Кенні (ADR-0010).

**Про числа.** Пілот і повний прогін на 100 фото CULane зроблено, параметри
p3 і p4 підібрано (`docs/experiments.md`). Числа нижче — звідти,
`results/summary.csv` і `results/c1_check.csv`. Значення параметрів у
описі методів — актуальні з `config.json`; чому саме такі — у журналі
експериментів.

## 1. Методи

### p3, стадія 1 — перспективне перетворення (`lanes/methods/perspective.py`)

**Ідея.** На фото смуги сходяться до горизонту; якщо «подивитися на дорогу
зверху», вони стають майже паралельними вертикальними лініями, і їх легко
шукати по стовпцях.

**Формула.** Точка `(x, y)` → `(x, y, 1)`, множимо на матрицю 3×3, ділимо на
третю координату: `u = (h11·x + h12·y + h13) / (h31·x + h32·y + 1)`, так само
`v`. Невідомих 8 (`h33 = 1`); кожна пара точок дає 2 рівняння, тож 4 пари —
система 8×8, розв'язуємо `np.linalg.solve`.

| Функція | Рядок | Що робить |
|---|---|---|
| `homography` | `perspective.py:18` | складає систему 8×8 і розв'язує її |
| `transform_points` | `perspective.py:46` | множить точки на матрицю й ділить на `w` |
| `top_view_rectangle` | `perspective.py:62` | 4 точки прямокутника виду зверху |
| `warp` | `perspective.py:76` | зворотне відображення з найближчим пікселем |

**Чому зворотне відображення.** Якщо йти від пікселів фото до результату,
далека частина дороги розтягується й у результаті лишаються дірки. Ідучи
від кожного пікселя результату назад у фото, значення отримує кожен.
Обернену матрицю окремо не рахуємо: `np.linalg.solve(matrix, target)`
розв'язує `matrix · p = p'` одразу для всіх пікселів.

**Параметри.**

- `p3.src` — трапеція дороги на фото (частки ширини й висоти). Низ на 0,70
  висоти — над капотом (нижня третина кадрів CULane — капот із
  відблисками); верх на 0,51 — трохи нижче точки сходу смуг (0,48).
- `p3.warp_size = [400, 600]` — розмір виду зверху. Він не залежить від
  розміру фото, тому параметри вікон у пікселях підходять і для кадру
  320×180, і для 1640×590.
- `p3.warp_margin = 0.1` — десята частина ширини зліва й справа; сусідні
  смуги вже всередині ширшої трапеції, тож великі відступи не потрібні.

### p3, стадія 2 — фільтр Прюітта (`lanes/methods/prewitt.py`)

**Ідея.** Контур — місце, де яскравість різко змінюється; рахуємо різницю
«праворуч мінус ліворуч» і «знизу мінус зверху».

**Формула.** Ядра `PREWITT_X = [[-1,0,1],[-1,0,1],[-1,0,1]]` і
транспоноване `PREWITT_Y` (`prewitt.py:12–13`); модуль
`sqrt(gx² + gy²)` (`prewitt.py:25`). Саму кореляцію з ядром робить
`filters.apply_kernel` Віталія.

**Відмінність від Собеля.** У Собеля центральний рядок має вагу 2
(згладжування з більшою вагою центру), у Прюітта всі три рядки рівні.

**Параметр.** `p3.prewitt_threshold = 0.2` — контуром вважаємо піксель із
модулем понад 20 % від найбільшого на кадрі (`prewitt.edges_above`). Поріг
відносний, тому темний кадр дає ті самі контури, що й світлий. 0,15 давав
кращий IoU на фото, але не проходив синтетичний сценарій із шумом — тому
0,2. На однотонному фото модуль ~1e-14, і `edges_above` не вважає це
контуром.

**Маска фото** (`p3_top_view.py:49–50`). Нижні кути виду зверху лежать поза
фото й заповнені нулями; межа «асфальт — нуль» дала б сильний хибний
контур. Тому так само деформуємо фото з одиниць, звужуємо результат ерозією
3×3 і лишаємо тільки контури всередині.

### p3, стадія 3 — гістограма стовпців і ковзні вікна (`lanes/methods/sliding_windows.py`)

**Ідея.** На виді зверху смуга майже вертикальна, тож у її стовпці багато
білих пікселів. Пік гістограми — початок смуги; далі йдемо вікнами вгору й
зсуваємо вікно за смугою.

| Функція | Рядок | Що робить |
|---|---|---|
| `column_histogram` | `sliding_windows.py:19` | сума білих пікселів по стовпцях нижньої половини |
| `find_base_peaks` | `sliding_windows.py:30` | найвищі піки з придушенням сусідів |
| `track_lane` | `sliding_windows.py:53` | вікна знизу вгору, центр — середнє `x` пікселів |
| `detect_lanes_top_view` | `sliding_windows.py:101` | усе разом + парабола `x = a·y² + b·y + c` |

**Параметри.**

- `max_lanes = 4` — CULane розмічає до 4 смуг.
- `peak_min_distance = 60` — ближчі піки вважаємо однією смугою: фільтр
  Прюітта дає два контури (лівий і правий край лінії фарби), і вони не
  мають стати двома смугами.
- `n_windows = 10` — 10 вікон по 60 рядків на 600 рядків виду зверху.
- `window_margin = 20` — вікно ±20 px від центру: вміщує обидва краї лінії
  фарби, але не сусідні контури (бордюр, машини).
- `min_pixels = 30` — менше пікселів у вікні — це шум: вікно не зсуваємо, а
  нижчий за 30 пік гістограми не вважаємо смугою.
- `poly_degree = 2` — парабола описує плавний поворот; пряма (ступінь 1)
  не описує, а ступінь 3 починає повторювати шум.

**Чому `x` від `y`.** Смуга майже вертикальна: для одного `y` рівно один
`x`, а для одного `x` може бути багато `y`.

### p4, стадія 1 — морфологічний top-hat (`lanes/methods/morphology.py`)

**Ідея.** Ерозія (мінімум у вікні) стирає світлі деталі, вужчі за вікно;
дилатація (максимум) повертає розмір тим, що вціліли. Різниця «оригінал
мінус відкриття» лишає тільки стерте — вузькі світлі смуги.

**Формула.** `opening = dilate(erode(gray))`, `top_hat = gray − opening`
(`morphology.py:27, 40, 48, 57`). Вікна будує `_windows`
(`morphology.py:11`) через `np.pad(mode="edge")` і `sliding_window_view`.

**Параметр.** `p4.tophat_width = 31` — горизонтальний елемент 1×31. Має
бути ширшим за лінію розмітки й вужчим за машини та небо, які треба
прибрати; саме значення перевіримо на фото в пілоті (T1). Елемент
горизонтальний, бо смуга вузька саме по горизонталі.

### p4, стадія 2 — метод Кенні (`lanes/methods/canny.py`)

| Крок | Рядок | Що робить |
|---|---|---|
| `gaussian_kernel` | `canny.py:26` | ядро `exp(−(x² + y²) / (2σ²))`, сума 1 |
| Собель | `canny.py:101` (усередині `canny`) | `gx`, `gy`, модуль і кут `atan2(gy, gx)` |
| `non_max_suppression` | `canny.py:51` | лишає піксель, не менший за двох сусідів уздовж градієнта |
| подвійний поріг | `canny.py:101` (усередині `canny`) | сильні ≥ `high · max`, слабкі ≥ `low · max` |
| `hysteresis` | `canny.py:76` | слабкий лишається, якщо з'єднаний із сильним |

**Параметри.** `canny_kernel = 5`, `canny_sigma = 1.4` — стандартне ядро
5×5 (σ = 1,4 якраз уміщується в радіус 2). `canny_low = 0.05`,
`canny_high = 0.1` — частки максимуму модуля після потоншення; Кенні у
своїй статті радить співвідношення порогів від 1 : 2 до 1 : 3. Низькі,
бо після top-hat найсильніший контур — край машини чи бордюр, і 30 % від
нього відсікало слабку розмітку вдалині.

**Чому гаусове згладжування дозволене.** Методи ЛР 5–6 заборонені як
окрема стадія, але викладачка дозволила гаусове згладжування всередині
Кенні й мін/макс усередині top-hat (AGENTS.md, правило 4).

**Захист від похибки округлення** (`ROUNDING_TOLERANCE`, `canny.py:23`). На
однотонному фото після згладжування сусідні пікселі різняться на ~1e-14, і
без цієї перевірки відносний поріг оголосив би контуром увесь кадр.

### p4, стадія 3 — перетворення Хафа (`lanes/methods/hough.py`, спільне)

**Ідея.** Пряму задаємо нормаллю: `ρ = x·cos θ + y·sin θ`. Кожен білий
піксель голосує за всі прямі, що через нього проходять; комірка `(ρ, θ)` з
найбільшою кількістю голосів — знайдена лінія.

| Функція | Рядок |
|---|---|
| `accumulator` | `hough.py:15` |
| `find_peaks` | `hough.py:55` |
| `peaks_to_lanes` | `hough.py:79` |
| `detect_lanes` | `hough.py:100` |

**Параметри (`hough`).** `theta_step_deg = 1`, `rho_step = 1` — точність
1° і 1 px. `min_angle_deg = 20` — відкидаємо майже горизонтальні лінії
(тіні, бампери, стоп-лінії). `min_votes = 40` — коротший за 40 px відрізок
не вважаємо смугою. `suppress_rho = 20`, `suppress_theta_deg = 5` — два
краї однієї лінії фарби не стають двома піками. θ беремо від −90° до 90°,
а не 0…180°, щоб майже вертикальна смуга не мала двох записів.

### Спільні модулі

- `roi.py` (`roi.py:11, 21, 34`) — трапеція з часток у пікселі, маска через
  `ImageDraw.polygon`, верхній рядок трапеції для Хафа.
- `synthetic.py:30` — кадр із відомою відповіддю: небо, асфальт, дві білі
  смуги; яскравість і шум із `seed`.
- `checks.py:32` — `mean_lane_offset`: для кожної еталонної смуги найближча
  знайдена за середнім `|Δx|` на рівнях `checks.offset_levels`.
- `report.py:50` — середні за (пайплайн, група) і за всіма групами.

## 2. Чому такий порядок стадій

**p3: перспектива → Прюітт → вікна.** Вікна шукають вертикальні смуги,
тому вид зверху має бути першим. Якщо спершу знайти контури на фото, а
потім деформувати бінарну маску, то найближчий піксель розмиває тонкі
контури далекої частини дороги нерівномірно (один піксель фото стає
десятком пікселів виду зверху), а товщина контурів залежить від відстані.
Вікна перед Прюіттом неможливі: їм потрібна бінарна маска.

**p4: top-hat → Кенні → Хаф.** Top-hat спершу прибирає все широке (небо,
машини, плавні тіні), тому Кенні бачить лише контури вузьких світлих
деталей. Якщо поміняти місцями — Кенні знайде контури всього, а top-hat по
бінарній масці тонких контурів (усі вужчі за 31 px) нічого не відсіє. Хаф
останній, бо йому потрібна бінарна маска контурів. ROI накладаємо після
Кенні, а не до: інакше межа трапеції сама стала б контуром.

## 3. Метрики

Порівнюємо дві маски 0/255: еталонну (розмітка CULane) і знайдену, обидві
намальовані лініями товщиною `masks.thickness = 16`.

```
MSE  = (1 / N) · Σ (I − K)²
PSNR = 10 · log10(255² / MSE)
SSIM = середнє по вікнах 7×7: ((2μxμy + C1)(2σxy + C2)) / ((μx² + μy² + C1)(σx² + σy² + C2))
IoU  = |A ∩ B| / |A ∪ B|
```

**Чому порожня маска має високий PSNR.** Для масок 0/255
`MSE = p · 255²`, де `p` — частка пікселів, що не збіглися, тож
`PSNR = 10 · log10(1 / p)`. Смуги займають лише кілька відсотків кадру:
якщо нічого не знайти, помилковими будуть тільки ці кілька відсотків. На
нашій вибірці порожня маска p0 має PSNR 14,78 дБ і SSIM 0,948 — більше,
ніж будь-який пайплайн, бо кожна хибна смуга додає хибні пікселі.

**Навіщо p0.** Це пайплайн, що не знаходить нічого. Його рядок показує,
який PSNR і SSIM дає «нічого не робити»; у сценарії `normal_group`
пайплайн мусить бути кращим за p0. IoU порожньої маски дорівнює 0, тому
IoU — головна метрика для висновків.

**Звідки 16 px.** Товщина лінії маски, задана в ТЗ і `config.json`
(`masks.thickness`); однакова для еталону й результату, тож жоден пайплайн
не може «намалювати собі» ширшу маску (ADR-0005).

## 4. Результати

100 фото CULane, усі параметри після підбору (T1, `docs/experiments.md`), IoU:

| Пайплайн | normal | crowd | shadow | curve | night | усі |
|---|---|---|---|---|---|---|
| p1 (Віталій) | 0.194 | 0.099 | 0.084 | 0.213 | 0.101 | 0.138 |
| p2 (Віталій) | 0.111 | 0.089 | 0.091 | 0.168 | 0.059 | 0.104 |
| **p3** | 0.207 | 0.068 | 0.056 | 0.249 | 0.208 | 0.158 |
| **p4** | 0.275 | 0.160 | 0.125 | 0.270 | 0.223 | 0.211 |
| p0 (нічого) | 0 | 0 | 0 | 0 | 0 | 0 |

Як підбирали: на 20 фото (кожне п'яте); на 80 інших IoU p3 — 0,149, p4 —
0,208, майже як на всіх 100, тобто параметри не підігнані під конкретні
кадри.

**p3 проти p4 — головне для захисту:**

- **p4 кращий майже скрізь** (0,211 проти 0,158). Top-hat прибирає небо,
  машини й плавні тіні ще до пошуку контурів, і Кенні дає тонкі контури
  саме розмітки.
- **На поворотах майже рівні** (p3 0,249, p4 0,270), хоча p3 повертає криві,
  а p4 — прямі. Ймовірне пояснення: розмітку CULane проведено лише до ~0,5 висоти
  кадру, і на цій ближній ділянці навіть поворот майже прямий.
- **У заторі й тіні p3 найслабший** (0,068 і 0,056): машини й тіні дають на
  виді зверху вертикальні контури, і ковзні вікна «з'їжджають» на них.
  Хафу ж досить кількох видимих відрізків прямої (ймовірна причина).
- **Уночі p3 близький до p4** (0,208 і 0,223) і вдвічі кращий за p1 і p2:
  поріг Прюітта відносний, тож слабка нічна розмітка однаково дає
  найсильніші контури на виді зверху.
- **Спільна зміна ROI** (обрізали капот) підняла p4 з 0,137 до 0,211 — те
  саме, що й підбір параметрів самого p4. p3 спільний ROI не використовує.
- **Час на фото:** p3 ≈ 36 мс, p4 ≈ 141 мс — найдовше гістерезис Кенні
  (поширення повторюється, доки маска змінюється). Час залежить від
  комп'ютера: у Віталія вийшло 23 і 97 мс.

**PSNR і SSIM.** Порожня маска p0 має PSNR 14,78 дБ і SSIM 0,948 — більше,
ніж будь-який пайплайн (p3 13,60 дБ, p4 13,34 дБ), бо кожна хибна смуга
додає хибні пікселі. Тому висновки робимо за IoU, а сценарій C1
`normal_group` не проходить жоден пайплайн — команда запропонувала
викладачці поріг за IoU.

Синтетичні сценарії (поріг 5 px): p3 — 3,04 / 3,04 / 4,55 px (прямі,
темрява, шум), p4 — 3,28 px у всіх. `python main.py check` — 11 з 16.

## 5. Обмеження й порівняння із сучасними підходами

- **p3:** трапеція `p3.src` фіксована — на підйомах, спусках і коли авто
  не по центру смуги вона «з'їжджає»; парабола не опише S-подібний
  поворот; пунктирна розмітка може не набрати `min_pixels` у вікні.
- **p4:** лише прямі — на далекій частині повороту пряма Хафа відходить
  від смуги; top-hat
  пропускає будь-які вузькі світлі деталі (стрілки, відблиски, тріщини);
  стерту чи закриту машиною розмітку не знайти.
- **Обидва:** параметри підібрані вручну й не адаптуються до кадру.
- **Нейромережі** (SCNN — автори CULane, F1 = 71,6 % на CULane; UFLD)
  навчаються на десятках тисяч розмічених кадрів і «домальовують» закриті
  смуги з контексту. Наші методи не потребують навчання й відеокарти,
  кожен крок можна пояснити, але на складних групах (ніч, затори) вони
  очікувано слабші. Джерела — `docs/related-work.md`.

## 6. Двадцять ймовірних питань

1. **Що таке ядро Прюітта й чим воно відрізняється від Собеля?** Ядро 3×3,
   що рахує різницю правого й лівого стовпців; у Собеля центральний рядок
   має вагу 2, у Прюітта всі ваги 1.
2. **Чому в гомографії 8 невідомих, а не 9?** Матриця визначена з точністю
   до множника (на `w` потім ділимо), тому фіксуємо `h33 = 1`.
3. **Чому потрібно саме 4 точки?** Кожна дає 2 рівняння, 4 точки — 8
   рівнянь на 8 невідомих. Три з них не можуть лежати на одній прямій.
4. **Що буде з фото 1×1?** Усі точки трапеції збігаються, система
   вироджена (`LinAlgError`); пайплайн повертає порожні стадії й нуль смуг
   (`p3_top_view.py`, блок `try`).
5. **Чому найближчий піксель, а не білінійна інтерполяція?** Простіше
   пояснити й достатньо: далі з виду зверху беремо лише контури. Білінійна
   дала б гладший результат — це можливе покращення.
6. **Чому гістограма лише по нижній половині?** Там смуги найближчі,
   найчіткіші й найменше викривлені поворотом.
7. **Що, як смуга переривчаста?** У вікні без пікселів центр не
   зсувається, наступне вікно шукає там само; парабола проходить через
   пікселі з інших вікон.
8. **Навіщо `peak_min_distance`?** Лінія фарби дає два контури поруч; без
   придушення вони стали б двома смугами.
9. **Чому парабола, а не пряма?** Пряма не опише поворот; на прямій дорозі
   коефіцієнт `a` просто близький до нуля.
10. **Що таке ерозія й дилатація?** Мінімум і максимум у вікні
    структурного елемента.
11. **Чому top-hat прибирає небо й машини?** Вони ширші за елемент 31 px,
    тож відкриття їх відновлює, і різниця дорівнює нулю.
12. **Чому елемент горизонтальний?** Смуга вузька по горизонталі й довга
    вздовж дороги; вертикальний елемент її б не стер.
13. **Чому не медіанний фільтр проти шуму?** Методи ЛР 5–6 заборонені як
    окрема стадія; дозволено лише гаус усередині Кенні.
14. **Навіщо потоншення в Кенні?** Градієнт дає «горб» у кілька пікселів
    завширшки; лишаємо вершину, щоб контур був завтовшки в один піксель.
15. **Навіщо два пороги?** Один високий поріг рве контур, один низький
    пропускає шум; гістерезис лишає слабкі пікселі тільки біля сильних.
16. **Чому напрям градієнта округлюємо до 4 значень?** У пікселя 8
    сусідів, тобто 4 прямі через центр: 0°, 45°, 90°, 135°.
17. **Чому в Хафі `ρ` і `θ`, а не `y = kx + b`?** Вертикальна лінія має
    нескінченний `k`; у нормальній формі всі прямі мають скінченні
    параметри.
18. **Що буде на повороті?** p3 повертає параболу й має впоратися; p4
    проведе пряму, що збігатиметься зі смугою лише поблизу авто.
19. **Чому ROI після контурів, а не до?** Межа обрізаного зображення сама
    дала б контур уздовж трапеції.
20. **Чому високий PSNR не означає гарний результат?** Смуги займають
    кілька відсотків кадру, тож і порожня маска p0 має PSNR близько порогу.
    Дивимося на IoU і на різницю з p0.

## 7. Мікрозавдання

**Змінити параметр.** Лише `config.json`, код не чіпаємо. Наприклад,
`p4.tophat_width` з 31 на 15 або `p3.n_windows` з 10 на 20. Перевірка:

```bash
python -m pytest tests/test_p3_top_view.py tests/test_p4_tophat.py
python main.py check
```

**Додати стадію.** Наприклад, вирівнювання гістограми перед top-hat у p4:

1. `lanes/pipelines/p4_tophat.py` — імпорт
   `from lanes.methods.histogram import equalize_histogram`;
2. після `gray = rgb_to_gray(image)` (рядок 20) додати
   `equalized = equalize_histogram(gray)` і передати `equalized` у
   `top_hat` (рядок 23);
3. додати `("equalized", equalized)` першим у список `stages`;
4. оновити таблицю p4 в `docs/pipelines.md` і список стадій у
   `tests/test_p4_tophat.py` та `tests/test_edge_cases.py`.

**Замінити метод.** Наприклад, Прюітт → Собель у p3:

1. `lanes/pipelines/p3_top_view.py` — замість імпорту з `prewitt` взяти
   `from lanes.methods.sobel import SOBEL_X, sobel_magnitude`;
2. рядок 42: `magnitude = sobel_magnitude(top_view)`;
3. рядок 48: розмір ядра брати з `SOBEL_X.shape[0]`.

Контракт масивів той самий (`np.float64 (H, W)`), тож наступні стадії не
змінюються. Перевірка після будь-якої зміни:

```bash
python -m pytest
python -m pylint lanes tools tests main.py
```

## 8. Запуск з нуля

```bash
git clone <посилання на репозиторій>
cd lane-detection-classical
python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
python -m pip install -r requirements.txt
python -m pytest                 # усі тести зелені
python main.py check             # синтетичні сценарії працюють без вибірки
```

З вибіркою в `data/sample/` (як її отримати — `docs/data.md`):

```bash
python main.py run --pipeline p3 --limit 10
python main.py run --pipeline all
python main.py report
python main.py check
```
